# Общий PDF-источник в рабочих панелях CueDeck

14 ноября 2026. Ветка work/shared-slide-source-20261114 от1c946f3. Это проверка production-built QA-копии настоящего приложения. Установщики и релиз не выпускались.

## Что подключено

| Путь | Результат |
| --- | --- |
| PGM оператора, Next, отдельное Preview | Получают готовые RGBA через порты |
| Зал и суфлёр | Один PDF/worker на ревизию; с15ноября один полноразмерный растр страницы для всех карточек |
| Next → PGM | Готовится в разрешении своего PGM, уменьшенный показ карточки; переход берёт тот же ключ |
| Скрытый Next оператора | Подготавливается без передачи пикселей |
| Смена Preview | Документ, worker и кэш PGM сохраняются |
| TAKE с наплывом | Подготовленная ревизия переносится в PGM без повторного открытия PDF |
| Потеря владельца | Последний кадр остаётся; owner и PDF-панели восстанавливаются |
| Возврат к изображению | PDF-ревизии удаляются, кэш и транспорт освобождаются |
| Таймер, заметки, видео, GIF, композиция | Прежние пути; ядро отвечает за статический PDF-слой |

Сначала один документ всё ещё декодировал страницу повторно для каждого размера:
cleanup выполнялся после каждого растра. Теперь у большого PDF максимум одна
декодированная страница живёт до другой страницы или300мс простоя. Это позволяет
переиспользовать decode между размерами и не держать несколько огромных страниц.
Собственные RGBA считываются до cleanup. Сам PDF.js/backend пока работает
в выделенном Electron renderer; внешний/native backend ещё не реализован.

## Shuttle: память настоящего приложения

Две разные PDF-ревизии, рабочие панели и Next; одинаковая последовательность
переходов. Контроль использует прежние независимые PdfLoader из той же сборки.
Последний вариант включает повторное использование decode между размерами.

| Пик выборок, МиБ | Прежние PdfLoader | Общий источник |
| --- | ---: | ---: |
| Сумма private bytes QA-процессов |7690|3162|
| System commit |11276|6420|

Снижение private bytes около59%. Это память процессов, не падение CPU на59%.
Цифры отличаются от первого скриншота прототипа8173→2899, потому что здесь реальные
панели разных размеров и другая нагрузка. Worker по-прежнему резервирует буфер
размера PDF; ограничения кэша RGBA не являются ограничением всей памяти процесса.

## Shuttle: время до рисования

По9переходов на каждый PDF. Время самого медленного из трёх окон, от начала
управления через CDP до drawImage/putImageData. Два RAF и физический экран не входят.
Небольшая выборка и последовательные прогоны не доказывают устойчивый выигрыш
на всех машинах. Качество с дополнительным PDF.js worker проверялось отдельно.

| PDF / readyMs | Прежние PdfLoader | Общий источник |
| --- | ---: | ---: |
|93: медиана|133,5|137,8|
|93: максимум|197,1|236,0|
|133: медиана|126,8|136,9|
|133: максимум|1525,0|868,0|
|133: первый подготовленный Next|126,8|48,4|

В этом сценарии основное подтверждённое преимущество: память и повторное
использование Next. Общий выигрыш скорости не заявляется. Первый продуктовый
вариант с cleanup после каждого размера давал максимум2439,5мс на большом PDF;
после повторного использования decode в данном прогоне868,0мс. Это сравнение
конкретных прогонов, не гарантия одинаковой задержки на каждой странице.

## 15 ноября: физический ТВ и общий полноразмерный кадр

Азат подтвердил картинку на LG TV1920×1080. Из-за отсутствия второго обнаруженного
экрана зал и суфлёр проверялись по очереди на одном ТВ. Заглушка через DP-переходник
не определилась, перезагрузка Shuttle не добавила второй экран; по решению Азата
дальнейшую проверку продолжили только с ТВ. После перезагрузки проверены SSH,
Sunshine и Disabled у MIDI-моста.

В оконном сравнении воспроизвели задержку оператора до650мс относительно MAIN:
MAIN имел готовый полноразмерный кадр, а изменившая размер карточка оператора
запрашивала другой PDF-растр. Исправление: общий кадр выходного разрешения для
PGM/Next всех панелей, уменьшение только при показе. Размер карточки берётся
в момент рисования, а не из уже устаревшего запроса.

оно не воспроизвелось ни глазами, ни по геометрии DOM. Это приёмка одного ТВ,

## 15 ноября: 30 минут непрерывной работы на Shuttle

Общий выходной растр проверен в отдельной QA-копии с тем же payload, что и
физический проход на ТВ. По 10 минут: большой PDF, малый PDF, снова большой.
Переходы каждые 2 секунды, обход вперёд и назад, заданные прыжки. Дважды выполнены
Preview другого файла и TAKE/Fade. Установленный CueDeck не заменяли.

340 выборок памяти. Пики первого и повторного большого PDF: 3180,3 и 3171,1 МиБ;
медианы последней минуты этих фаз: 2852,7 и 2968,3 МиБ. За этот проход роста пика
не увидели. Полчаса не доказывают отсутствие утечки на многочасовом мероприятии.
Это измерение общего растра; нового парного A/B с legacy здесь нет, снижение CPU
по этому проходу не заявляется. Сверка окон подтверждает одинаковые кадры;
независимый прежний PdfLoader проверялся отдельным проходом выше.

После последнего кадра стенд вызвал app.exit напрямую и обошёл штатную очистку:
в журнал попали owner recovery и IPC к уже закрытым окнам. Ошибок во время
показа не было. Контроллер исправлен для выхода через штатный quit guard;
перед ожиданием PID отключает inspector, который иначе удерживает Node при выходе.
Отдельный повтор: 25,395 с, 23 шага, два TAKE, шесть сверок кадров. GUI завершился,
весь app.log без ошибок, установленный ASAR не изменён. Сам PDF-payload остался
тем же. Эти исправления стенда не выдаются за новый 30-минутный прогон.

Потеря SSH ближе к концу не остановила локальный контроллер. На Mini временно
исчез линк Ethernet; причина не установлена. После возвращения доступа отчёт
скопирован и проверен по SHA256, все JSONL прочитаны без оборванных строк.
Сырые данные: generated/product-pdf-qa/soak-30m-20261115. Архив отчётов:
SHA256 a1a0d27a3e1a47a9fb40c4c8c6a15450bbe4d5b06e3ff3b0d5db037d28910300.

## 15 ноября: Mac, iPad и заглушка

Три независимых дисплея: встроенный Retina, заглушка с физическим режимом4K
и iPad через Sidecar. Оператор оставался на Mac; MAIN и суфлёр менялись местами
между iPad и заглушкой. Азат подтвердил суфлёр на iPad и MAIN на весь экран.
Выход заглушки проверялся захватом окна; физического монитора за ней нет.

В первом варианте размер PDF-кадра зависел от дисплеев. Заглушка подняла его
до3840×2160, а быстрое пролистывание обнаружило заполненный удержаниями кэш.
Азат уточнил предел1080p. Общий PDF-растр теперь вписывается в1920×1080;
масштаб Retina и разрешение выхода меняют только показ. Дополнительно при
давлении на кэш снимаются удержания подготовленных Next, затем повторяется
актуальный запрос. Уже переданные пиксели остаются у получателей. Для этого
