# Проверка готового релиза CueDeck

Эти проверки запускают установленную программу на Mac и Windows. Они дополняют Vitest: проверяют реальный IPC, отрисовку, декодирование, файлы проекта и сетевой выход. Исходники CueDeck во время такого прогона не импортируются.

## После релиза

Наблюдатель `local.cuedeck.release-qa` подготовлен, но пока не включён: первая сквозная проверка остановилась на начальной подготовке приложений. После приёмки он сможет раз в 5 минут смотреть последний опубликованный стабильный релиз GitHub. Модели ИИ и платные API для этого не нужны.

Прогон начинается, когда обе установленные копии обновлены штатным процессом релиза и общая блокировка `active.lock` свободна. Сам runner не публикует релизы и не устанавливает приложения. Пока идёт другой тест, он оставляет заявку в очереди. Версии, SHA256 исполняемого файла и app.asar должны совпасть с проверенными GitHub-архивами; одного совпадения номера версии недостаточно.

Каждый релиз проверяется один раз. После ошибки нет автоматических повторов: сначала читаем отчёт, разбираем причину, затем явно запускаем повтор с `--retry`.

## Сценарии на каждой ОС

| Сценарий | Что проверяет |
| --- | --- |
| Установленная копия | Версия, путь, SHA256 архива и установленного содержимого |
| Три роли | Реальные окна оператора, зала и суфлёра |
| Превью и TAKE | Загрузка в превью сохраняет старую картинку в зале; кнопка TAKE выдаёт новую |
| PDF | Три страницы с известными цветами, возврат назад, пиксель выходного кадра |
| Картинка | Открытие и выдача через Fade, пиксель зала |
| PPTX | Настоящая конвертация LibreOffice и цвет двух страниц на выходе |
| Видео | Декодирование, движение времени, пауза, перемотка, немой суфлёр |
| Blackout | Чёрный пиксель зала и mute видео |
| Таймеры и сообщение | Ход/пауза, отдельный таймер зала, сообщение на суфлёре |
| HTTP | Команды меняют настоящий таймер и blackout, проверяется кадр |
| OMT | Видео и стерео 440/880 Гц из CueDeck принимаются независимым SDK на другой машине |
| Проект | Сохранение и открытие, четыре материала, кириллица, персональный фейд |
| Холодный запуск | Закрытие приложения штатным кодом, новый процесс, восстановление списка и фейда |

Тестовые материалы создаются заново: PDF, PNG и PPTX без пользовательского содержимого, 16-секундный H.264/AAC-ролик с FFmpeg. Цвета сравниваются со снимком композитора Chromium, а не только с номером слайда в состоянии.

Во время Save/Open подставляется только ответ системного выбора файла. Запись, чтение и восстановление выполняет установленный CueDeck. Сам нативный диалог этим не проверяется. Штатное закрытие проходит через loopback-инспектор проверенной установленной копии. Для первого запуска на каждой машине CueDeck нужно закрыть вручную; запущенную без инспектора копию runner оставляет в BLOCKED. Права и настройки безопасности он не меняет, принудительного завершения приложения нет.

OMT-приёмник проверяет старт, движение кадров, длительность PCM, частоты каналов, тишину и непрерывность временных меток. Первые 1,5 секунды не входят в счётчики содержимого; время старта и PTS проверяются отдельно. Это цифровая проверка сетевого выхода, без утверждения о физическом звуке или задержке до телевизора.

## Запуск и отчёт

На машине-контроллере нужен Python 3.9+, FFmpeg и настроенный SSH к Windows. Адреса, SSH-алиас и пути лежат только в локальном конфиге, в репозиторий их не добавляем.

```sh
python3 controller.py poll --config /absolute/path/config.json
python3 controller.py status --config /absolute/path/config.json
python3 controller.py stop --config /absolute/path/config.json
python3 controller.py run --tag vX.Y.Z --retry --config /absolute/path/config.json
```

Конфиг содержит `root` общей папки стенда, `repository` в формате owner/repo, `windowsHost` (SSH alias), `windowsRoot` (абсолютный путь без пробелов), `miniAddress`, `windowsAddress` и `ffmpeg` (абсолютный путь). Windows helpers и `receiver.cjs` предварительно кладутся в `windowsRoot`. PowerShell-файлы передаются с UTF-8 BOM, потому что Windows PowerShell 5.1 иначе портит кириллицу.

`install-watcher` устанавливает LaunchAgent текущего пользователя; повторную установку поверх существующего он отклоняет. Остановка наблюдателя: `launchctl bootout gui/$(id -u)/local.cuedeck.release-qa`. Она не останавливает другой тест стенда. `stop` ставит STOP только текущему релизному прогону.

В `runs/release-<tag>-<UTC>/` сохраняются манифест сборок и скриптов, результаты каждого сценария, снимки, ошибки и SHA256. `release-status.json` показывает ход, `release-queue.json` причину ожидания. В отчёте есть PASS, FAIL и BLOCKED. Пустой отчёт, пропущенный обязательный сценарий и ошибка уборки не становятся PASS. Автоматическая отправка сообщений не включена.

Проверки самой обвязки запускаются из корня репозитория:

```sh
npm run test:release-qa
```

Они проверяют в том числе отрицательные случаи: неверный цвет/повреждённый PNG, неправильный хеш при той же версии, незавершённый набор, занятую блокировку и запрет автоматического повтора ошибки. CI запускает их отдельно от Vitest. Сетевые проверки выполняются на домашнем стенде, не на GitHub runner.

## Пока не проверяется

566 существующих Vitest-проверок, TypeScript и 17 проверок обвязки прошли 25 октября 2026 года. Полный набор живых сценариев ещё не принят. В первой репетиции проверены хеши опубликованных архивов и установленных программ, а занятый стенд корректно дал ожидание. macOS отказала osascript в Accessibility; Windows показала команду выхода как UIA Pane без InvokePattern. Попытка автоматизировать первоначальные нативные диалоги исключена из финального runner. Перед включением наблюдателя нужны ручной первый выход, полные Mac/Windows-прогоны и проверка уборки.

При следующем обновлении обе тестовые копии нужно запускать через подготовленный QA launcher с loopback-портами. Обычный запуск без инспектора снова потребует ручного выхода. Пока эта часть выпуска ещё не закреплена в действующем релизном процессе.

Физическое изображение/звук на телевизоре, A/V-задержка, настоящий кликер и Stream Deck, USB-капчер, нативный Intel Mac, реальная публикация на видеоплощадки и полный рабочий день под нагрузкой требуют отдельных сценариев. Скриншот и цифровой PCM не заменяют эти измерения. Native MediaCore из соседнего эксперимента к проверке выпущенного CueDeck не подключается.
